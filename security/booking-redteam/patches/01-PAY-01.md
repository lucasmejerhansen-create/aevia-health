# PAY-01 [HØJ] — Stripe-webhook validerer ikke beløb/valuta/pakke

**Status:** FORSLAG (ikke anvendt). Live-koden i `api/` er IKKE rørt.
**Kræver:** review + ende-til-ende-test i Stripe-testmiljø før merge.

---

## Sårbarhed

Webhooken behandler enhver gyldigt signeret `checkout.session.completed` som
**fuld betaling** uden at krydstjekke det faktisk betalte beløb (`s.amount_total`)
og valuta (`s.currency`) mod den forventede pris for den pakke/gavekort/tilvalg
der blev bestilt. `amount_total` bruges udelukkende til at formatere
bekræftelsesmailen — aldrig til validering.

En Stripe-signatur beviser kun, at Stripe sendte eventet — ikke at det rigtige
beløb blev betalt. Den er derfor ingen beskyttelse mod denne misbinding.

### Fil:linje

| Fil | Linje | Problem |
|---|---|---|
| `api/stripe-webhook.js` | 150–160 | `markPaid` / `setBookingPaid` kaldes uden beløbs-, valuta- eller pakke-tjek |
| `api/stripe-webhook.js` | 166 | `s.amount_total` bruges KUN i mailen, aldrig til validering |
| `api/checkout.js` | 133 | `?bid` → `metadata.booking_id` (kun `.slice(0,40)`), ingen prisbinding; `?bid` vedhæftes endda også på gavekort-checkout |
| `api/book-slot.js` | 153–158, 174, 200 | `isPaid` (vilkårlig truthy) → `payUrl=null`, `paid:true` uden at sammenligne med bookingens pakkepris |
| `api/_booking-store.js` | 501–523 | `markPaid` / `isPaid` / `setBookingPaid` gemmer/tjekker ingen pris eller pakke |

---

## Repro

### Variant A — booking_id-kapring (krydsbinding pris ↔ booking)

1. Angriber booker en dyr pakke via `POST /api/book-slot`
   (fx Aevia Elite, 36.995 kr) → får `r.id`.
2. I stedet for det udleverede `payUrl` (`?pkg=elite&bid=<id>`) åbner angriber
   `/api/checkout?pkg=gavekort&beloeb=1000&bid=<id>` — `checkout.js:133` lægger
   `<id>` i `metadata.booking_id`, men opkræver kun **1.000 kr**.
3. Angriber gennemfører den rigtige 1.000-kr-betaling → Stripe sender et
   **gyldigt signeret** `checkout.session.completed`.
4. `stripe-webhook.js:156-158` kalder `setBookingPaid(<id>)` →
   Elite-bookingen får `paid:true` uden pristjek.

### Variant B — e-mail pre-pay (pris-agnostisk paid-markør)

1. Angriber betaler ét gavekort på 1.000 kr med sin e-mail.
2. Webhook linje 155: `markPaid(email)` sætter `paid:<email>` i **180 dage**.
3. Næste `POST /api/book-slot` med samme e-mail rammer `isPaid()=truthy`
   (`book-slot.js:154`) → `payUrl=null` (158), `setBookingPaid(r.id)` (155),
   og bekræftelsesmailen viser "Betaling registreret" (`paid:true`, 174)
   for et vilkårligt dyrt forløb.

---

## Impact

Direkte betalings-integritets-/indtægtstab. En angriber kan få et forløb til op
til **36.995 kr** (Aevia Elite) — eller enhver booking knyttet til e-mailen —
bekræftet som **fuldt betalt** ved kun at gennemføre en reel betaling helt ned
til 1.000 kr. Bookingen markeres `paid:true` (vises i admin/klinik som betalt),
kunden får ingen yderligere opkrævning, og klinikker udfører dyre ydelser
(MRI, genetik, VO2max) i tillid til paid-status. Gentageligt; kræver kun et
gyldigt kort og én lille, ægte Stripe-betaling. Signaturkontrollen forhindrer
ikke angrebet, da begge varianter bruger ægte, signerede events.

---

## Fix

Princippet: **"paid" skal være pris-bindende.** To uafhængige lag:

1. **Session-niveau** (webhook): genberegn forventet pris serverside ud fra
   `PACKAGES`/`GIFTCARDS`/`ADDONS` og afvis events, hvor `amount_total` ikke
   dækker det bestilte. Dette stopper underbetaling af en pakke direkte.
2. **Booking-binding** (`setBookingPaid`): det betalte beløb skal dække
   **bookingens egen pakkepris**, før bookingen markeres betalt.

> **Vigtigt om Variant A:** session-niveau-tjekket alene stopper IKKE
> kaprings-varianten, fordi et 1.000-kr gavekort ER en gyldig 1.000-kr betaling
> (`amount_total == expectedAmount(gavekort)`). Det er **lag 2** —
> `setBookingPaid(id, amount)`, der sammenligner mod Elite-prisen (36.995 kr) —
> der lukker hullet. Begge lag skal med; pkt. 4 (drop `?bid` på gavekort) er
> et ekstra forsvar i dybden.

For at undgå at duplikere priskataloget flyttes `PACKAGES`/`GIFTCARDS`/`ADDONS`
ud i et delt modul `api/_pricing.js`, som både `checkout.js` og
`stripe-webhook.js` importerer. (Diffen nedenfor viser kun de
sikkerheds-relevante ændringer; selve udflytningen er mekanisk.)

### 0) Nyt delt modul — `api/_pricing.js`

```js
// api/_pricing.js — ÉN autoritativ priskilde (flyt PACKAGES/GIFTCARDS/ADDONS
// hertil fra checkout.js, og importér begge steder).
export const PACKAGES = { /* core, executive, elite — uændret fra checkout.js */ };
export const GIFTCARDS = { /* 1000, 2500, 5000, core, plus — uændret */ };
export const ADDONS = { /* vo2max, hormon, mri, genetik, followup — uændret */ };

// Forventet totalbeløb (øre) for en checkout-session ud fra dens metadata.
// Returnerer null hvis metadata peger på en ukendt pakke/gavekort.
export function expectedAmount({ pakke, gavekort, tilvalg }) {
  if (pakke === "gavekort") {
    const g = GIFTCARDS[String(gavekort || "").toLowerCase()];
    return g ? g.amount : null;            // gavekort har ingen tilvalg
  }
  const base = PACKAGES[String(pakke || "").toLowerCase()];
  if (!base) return null;
  const addons = String(tilvalg || "").split(",").map((k) => k.trim().toLowerCase())
    .filter((k) => ADDONS[k]).reduce((sum, k) => sum + ADDONS[k].amount, 0);
  return base.amount + addons;
}

// Pakkepris (øre) for en bookings pakke-slug (book-slot bruger 'plus' alias).
const PKG_ALIAS = { core: "core", executive: "executive", plus: "executive", elite: "elite" };
export function packageAmount(slug) {
  const p = PACKAGES[PKG_ALIAS[String(slug || "").toLowerCase()]];
  return p ? p.amount : null;
}
```

> **Bemærk om moms:** hvis `STRIPE_ENABLE_TAX=true`, lægger Stripe 25 % oven i
> `unit_amount` (`tax_behavior: "exclusive"`), så `s.amount_total` >
> `expectedAmount`. Brug derfor `>=`-sammenligning (ikke `===`) — se nedenfor.

## Regressions-risiko (delt kode)

- **`_booking-store.js` (`setBookingPaid`)** er delt mellem `stripe-webhook.js`
  og `book-slot.js`. Signaturen får et **valgfrit** 2. argument; ved manglende
  argument bevares den gamle adfærd, så ingen eksisterende kald knækker. Begge
  kaldssteder opdateres til at sende et beløb.
- **`packageAmount`/`expectedAmount`** importeres nu fire steder. Hvis priserne
  i `PACKAGES`/`GIFTCARDS`/`ADDONS` flyttes til `_pricing.js`, SKAL `checkout.js`
  importere derfra i stedet for sin egen lokale kopi — ellers divergerer
  priserne (en pris-drift mellem checkout og webhook ville selv blive en bug).
  Anbefaling: én kilde, ingen kopi.
- **Moms (`STRIPE_ENABLE_TAX`)**: `amount_total` kan være højere end
  `expectedAmount`. Derfor `>=`, ikke `===`. Hvis I senere indfører rabatkoder
  via Stripe, kan `amount_total` blive **lavere** end katalogprisen — så skal
  validering tage højde for `total_details.amount_discount`.
- **Legacy paid-markører** (sat før fixet) mangler `amount`. Med
  `Number(undefined) >= need` → `NaN >= need` → `false`, så en gammel
  pris-agnostisk markør holder IKKE længere som "fuldt betalt" i book-slot.
  Det er den ønskede (sikre) adfærd, men kan i en kort overgang få ægte
  før-betalte kunder til at se et betalingslink — overvåg supporthenvendelser
  i 180 dage efter deploy (markørens TTL).
