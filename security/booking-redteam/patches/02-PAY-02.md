# PAY-02 — Manglende idempotens på Stripe-webhook (replay → dublerede mails)

- **Sværhedsgrad:** lav
- **Status:** bekræftet i kode
- **Komponent:** `api/stripe-webhook.js`, `api/_booking-store.js`
- **Type:** manglende idempotens / replay af signeret event

> Dette er et FORSLAG. Live-koden i `api/` er IKKE redigeret. Diffen nedenfor er
> klar til at anvende, men skal review'es (og mod-mappes mod Stripes faktiske
> retry-adfærd) før den lægges live.

---

## 1. Sårbarhed

Stripe-webhook-handleren verificerer kun event-signaturen. Den dedup'er ikke på
`event.id`. `stripe.webhooks.constructEvent` validerer HMAC + timestamp-tolerance
(default 300 s), men det er dokumenteret Stripe-adfærd at samme event kan blive
leveret mere end én gang (Stripes egne retries ved timeout/transient fejl, samt
en angriber der genafspiller en opfanget, gyldigt signeret leverance inden for
~5-minutters-vinduet).

De to data-mutationer i `completed`-grenen er reelt idempotente:

- `markPaid` (`_booking-store.js:501-505`) er et ubetinget `SET paid:<email>` —
  overskriver samme værdi, ingen skade ved gentagelse.
- `setBookingPaid` (`_booking-store.js:514-523`) har en `if (b.paid) return`-guard.

**Men bivirkningerne er ikke idempotente:**

- `sendMail` (`stripe-webhook.js:161-167` → `:98-105`) POST'er ubetinget en ny
  "Din booking hos Aevia er bekræftet"-mail til kunden + bcc `kontakt@aevia.dk`
  ved hvert gennemløb.
- `upsertCustomerContact` (`stripe-webhook.js:172` → `:110-124`) re-kører.

Desuden sluges mail-fejl (`:168-170`) og handleren returnerer altid `200`, så
Stripes egne retries primært reproducerer dubletten frem for at fejle synligt.

Der findes intet processed-event-lager i `api/` (grep på
`event.id` / `processed` / `idempot` / `dedup` / `seen` / `wh:` gav 0 relevante
træf — kun urelateret graph-traversal i `_engine.mjs` og svc-dedup i
`reserveMulti`). Webhooken importerer ikke `_ratelimit.js`, og rate-limit ville
alligevel ikke dedup'e signerede replays.

## 2. Repro

**Realistisk (uden angriber).** Stripe genleverer samme `event.id` ved sin egen
retry-logik — fx hvis funktionen timer ud før svar, eller ved en transient
leveringsfejl. Hvert gennemløb POST'er en ny bekræftelsesmail til kunden + bcc
`kontakt@aevia.dk` og kalder `upsertCustomerContact` igen.

**Angriber-drevet.**
1. Fang én gyldigt signeret leverance af `checkout.session.completed` (rå
   request-body + `Stripe-Signature`-header via proxy/log/kompromitteret
   retry-vej).
2. Inden for signaturens timestamp-tolerance (~5 min) gen-POST
   `https://aevia.dk/api/stripe-webhook` med nøjagtig samme raw body og samme
   `Stripe-Signature` → `constructEvent` verificerer igen → `200`.
3. Gentag N gange inden for vinduet → N ekstra bekræftelsesmails.

Data-mutationerne forbliver korrekte (idempotente); kun mails + kontakt-upsert
duplikeres.

Den automatiserede regressionstest er
`security/booking-redteam/tests/PAY-02.test.mjs` — den kører handler-logikken to
gange med samme `event.id` og hævder, at `sendMail` kun POST'es én gang.

---

## 3. Impact

Dublerede transaktionsmails til kunden + bcc-støj til `kontakt@aevia.dk`; mild
kundeforvirring og potentielt øget Resend-forbrug. Ingen finansiel- eller
dataintegritetspåvirkning (markPaid/setBookingPaid er idempotente). Bounded blast
radius. Det realistiske trigger er Stripes godartede retries snarere end en
privilegeret angriber — derfor **lav** sværhedsgrad.

---

## 4. Fix

Tilføj idempotens på `event.id` FØR `completed`/`expired`-grenene kører
bivirkninger. Genbrug det allerede tilgængelige Redis-lag (`_booking-store.js`)
og det eksisterende NX-lås-mønster fra `cancel` (`_booking-store.js:340`):
`SET wh:<event.id> "1" NX EX <7 dage>`. Returnerer Upstash `"OK"` → første gang
(vi fortsætter); `null` → allerede set (vi returnerer 200 uden bivirkninger).

Markøren sættes EFTER vellykket `constructEvent` (så uverificerede payloads aldrig
låser en `event.id`) og FØR `sendMail` (så replay ikke når frem til mailen).

`fail-open`-detalje: hvis Redis ikke er konfigureret / fejler, bevarer vi
nuværende live-adfærd (vi sender mailen) frem for at tabe en legitim
førstegangs-bekræftelse. Det er bevidst: PAY-02 er lav, og en tabt
bekræftelsesmail er værre end en sjælden dublet ved Redis-nedetid.

### 4a. `api/_booking-store.js` — ny eksporteret helper

```diff
@@ api/_booking-store.js  (efter setBookingPaid, ~linje 523)
   export async function setBookingPaid(id) {
     if (!isConfigured() || !id) return { ok: false };
     const raw = await redis(["GET", `bk:${id}`]);
     if (!raw) return { ok: false };
     const b = JSON.parse(raw);
     if (b.paid) return { ok: true, booking: b };
     b.paid = true;
     await redis(["SET", `bk:${id}`, JSON.stringify(b), "KEEPTTL"]);
     return { ok: true, booking: b };
   }
+
+// ── Webhook-idempotens (Stripe leverer events >1 gang) ───────────────────────
+// Markér en event.id som behandlet — atomisk via SET ... NX EX (samme mønster
+// som aflysnings-låsen cxl:<id>). Returnerer true KUN ved første leverance, så
+// kalderen kan springe bivirkninger (mail, kontakt-upsert) over ved replay.
+// Fail-OPEN: uden Redis / ved fejl returneres true, så en legitim
+// førstegangs-bekræftelse aldrig tabes (PAY-02 er lav; tabt mail > sjælden dublet).
+export async function markEventProcessed(eventId, ttlSeconds = 60 * 60 * 24 * 7) {
+  if (!isConfigured() || !eventId) return true;
+  try {
+    const r = await redis(["SET", `wh:${eventId}`, "1", "NX", "EX", ttlSeconds]);
+    return r === "OK"; // null ⇒ allerede behandlet
+  } catch (e) {
+    console.error("markEventProcessed-fejl:", e && e.message);
+    return true; // fail-open
+  }
+}
```

## 5. Regressions-risiko (delt kode)

`markEventProcessed` er en **ny** eksport i den delte `_booking-store.js` — den
ændrer ingen eksisterende funktion, så `markPaid`, `setBookingPaid`,
`reserveMulti`, `cancel` m.fl. er adfærdsmæssigt uberørte. Lav risiko.

Ting at være opmærksom på:

- **TTL-kollision i nøglerum.** Ny nøglepræfiks `wh:` deler ikke navn med
  eksisterende præfikser (`cnt:`, `blk:`, `bk:`, `day:`, `cxl:`, `paid:`,
  `pend:`, `rules:`, `wait:`, `calcache:`). Ingen kollision.
- **Fail-open er bevidst, men en svaghed.** Ved Redis-nedetid genåbnes dublet-
  hullet (vi sender alligevel). Det matcher den eksisterende fail-open-filosofi
  for ikke-kritiske stier og holder PAY-02 lav. Hvis man senere vil have hård
  garanti, kan man kombinere med at returnere non-2xx ved `sendMail`-fejl (så
  Stripe-retry ér ufarlig, fordi idempotens dækker den) — men det er en separat,
  større ændring.
- **`event.id`-stabilitet.** Stripe garanterer at retries af samme leverance
  bærer samme `event.id`; det er netop dedup-nøglen Stripe selv anbefaler. Ingen
  antagelse ud over dokumenteret adfærd.
- **Test-coupling.** Regressionstesten importerer ikke live-modulerne (de kræver
  Stripe/Redis-env og er ESM med side-effekt-import af `stripe`). Den
  reproducerer i stedet handler-kontrakten med en minimal in-memory Redis-mock
  og en `sendMail`-spion, så den fanger regressionen uden netværk. Se filens
  kommentar for den nøjagtige mapping mod live-linjerne.
