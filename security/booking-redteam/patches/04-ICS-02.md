# ICS-02 — DNS-rebinding / TOCTOU i `fetchBusy` (SSRF-værn pinner ikke IP)

- **Alvorlighed:** Lav (defense-in-depth-svaghed; kræver autentificering + race-vinding)
- **Type:** SSRF via DNS-rebinding / TOCTOU
- **Status:** Bekræftet i kode
- **Patch-status:** FORSLAG — IKKE anvendt på live-kode. Diff nedenfor er klar til review/anvendelse.

> Dette er et patch-forslag. Live-koden under `api/` er **ikke** ændret. Regressionstesten
> ligger i `security/booking-redteam/tests/ICS-02.test.mjs`.

---

## Sårbarhed

`fetchBusy` validerer host-navnet med ét DNS-opslag, men forbinder bagefter med
global `fetch`, der laver et **separat, uafhængigt** DNS-opslag. Den validerede IP
pinnes ikke til den IP, der reelt forbindes til. En angriber-kontrolleret host med
lav TTL kan returnere en offentlig A-record til vagt-opslaget og en privat
(169.254.169.254 / 10.x / 127.x) til selve forbindelsen — klassisk
DNS-rebinding/TOCTOU.

### Fil:linje

`api/_calendar.js`

- Linje **179**: validerings-opslaget (`dns.lookup(host, { all: true })`) — resultatet
  bruges KUN til `some(ipPrivate)`-tjekket og **kasseres** derefter.
- Linje **185**: `fetch(u, ...)` laver et **nyt** opslag på forbindelsestidspunktet via
  den bundlede undici-resolver. `ipPrivate`/`ipv4Private` (131–151) er korrekte, men
  anvendes på det forkerte (første, kasserede) opslag.

**Bekræftet i repoet:** `grep -rn "setGlobalDispatcher\|undici\|new Agent\|Dispatcher"`
giver tomt → ingen custom dispatcher/lookup/connect. Node v24.16.0 → global `fetch`
(undici 7.25.0) re-resolver selv via OS-resolveren uden kendskab til det forudgående
`dns.lookup`-resultat. `redirect:manual` (186) og port/https-tjek (165–167) lukker
andre vektorer, men ikke denne.

### Leak-kanal og re-fetch-stier

- **Leak-oracle:** `api/clinic-portal.js:130-134` — `action:"testcal"` returnerer
  `{ ok:true, events: busy.length }` → lækker et heltals-event-tal som svag oracle.
- **Re-fetch (uafhængigt af testcal-cache):** `api/_booking-store.js:146` (`busyFor`)
  og `api/_booking-store.js:261` (`reservePart`) kalder `fetchBusy(c.calUrl)` på en
  persisteret URL (gemt via `saveRules`, `_booking-store.js:423`), så racet kan vindes
  uafhængigt af `testcal`-svaret.

## Repro

**Forudsætning (bekræftet):** gyldigt `CLINIC_TOKENS` bearer-token (rogue/kompromitteret
partnerklinik). Der er **ingen uautentificeret** sti til `fetchBusy` — alle
`clinic-portal` POST-actions kræver `accessForToken` (`clinic-portal.js:110-111`).

1. Registrér et domæne med autoritativ DNS, **TTL=0-1s**, der skifter mellem en
   offentlig IP og fx `169.254.169.254`.
2. `POST /api/clinic-portal` med
   `{ action:"testcal", calUrl:"https://rebind.attacker.tld/cal.ics" }`
   og `Authorization: Bearer <token>`.
   `normalizeIcsUrl` godkender (https, port 443, `hostAllowed=true`, da ikke IP-literal).
   `dns.lookup` (179) rammer (forhåbentlig) den offentlige record → består.
   global `fetch` (185) laver nyt opslag → kan ramme den private record → forbinder internt.
   Svaret `{ok:true, events: busy.length}` lækker et heltal som svag oracle; ellers blind.
3. Vind racet ved gentagelse; alternativt gem URL'en via `action:"saveRules"`
   (persisteres som `calUrl`) og ram den via live re-fetch i
   `reservePart`/`busyFor` (`_booking-store.js:261`/`146`).

---

## Impact

Autentificeret (rogue partnerklinik) blind/semi-blind SSRF mod interne ressourcer
(cloud-metadata `169.254.169.254`, interne services, loopback) **trods** SSRF-værnet.
Eksfiltration begrænset til event-tæller (heltal) via `testcal`-svar — ikke body-indhold.

**Mitigerende:** kræver autentificering (ikke internet-vendt), race-afhængigt (ikke
deterministisk), `redirect:manual` + https-only + port-443-only lukker lettere vektorer.
Defense-in-depth-svaghed, ikke umiddelbart kritisk.

---

## Fix

**Kerneidé:** Brug *samme* DNS-resolution til både validering og forbindelse — pin den
validerede IP til selve TCP-forbindelsen, så TOCTOU-vinduet forsvinder.

To realistiske veje:

### Anbefalet (afhængigheds-fri): `node:https` + pinnet IP + SNI

Projektet har bevidst minimale dependencies (`stripe` only) og `undici` er **ikke**
installeret som pakke (`import('undici')` → `ERR_MODULE_NOT_FOUND`). Derfor undgår den
anbefalede patch en ny afhængighed: vi slår op én gang, validerer **alle** returnerede
adresser, og forbinder via `node:https` til den **pinnede IP** med `servername` (SNI) +
`Host`-header, så TLS-certifikatet stadig valideres mod værtsnavnet.

Bekræftet at `https.request({ host: <ip>, servername: <host>, headers:{Host:<host>} })`
giver gyldig TLS-handshake og status 200 mod en offentlig vært på Node v24.16.0 — dvs.
cert-validering bevares selvom vi forbinder til en IP-literal.

**Hvorfor dette lukker TOCTOU:** valideringen (`resolvePinnedIp`) og forbindelsen
(`httpsGetPinned` med `host: ip`) bruger **samme** IP. Der sker ingen anden DNS-resolution
mellem validering og connect, så et rebind kan ikke ramme. `servername` + `Host`-header
bevarer korrekt TLS-cert-validering mod værtsnavnet (bekræftet status 200 mod offentlig vært
på Node v24.16.0). `redirect:manual`-adfærd bevares (3xx → `[]`). https-only og port-443
håndteres fortsat i `normalizeIcsUrl`.

### Alternativ (hvis `undici` tilføjes som dependency)

```js
import { Agent } from "undici";
// lookup kører på FORBINDELSESTIDSPUNKTET → validering + connect bruger samme opslag.
const pinnedAgent = new Agent({
  connect: {
    lookup(host, opts, cb) {
      dns.lookup(host, { all: true, ...opts }, (err, addrs) => {
        if (err) return cb(err);
        const list = Array.isArray(addrs) ? addrs : [{ address: addrs, family: opts.family || 4 }];
        if (!list.length || list.some((a) => ipPrivate(a.address))) {
          return cb(new Error("blocked private address"));
        }
        cb(null, list[0].address, list[0].family); // forbind til den validerede adresse
      });
    },
  },
});
// ...
const r = await fetch(u, { redirect: "manual", signal, dispatcher: pinnedAgent, headers: {...} });
```

Bemærk: dette kræver `undici` som direkte dependency (i øjeblikket **ikke** installeret;
kun `stripe` står i `package.json`). Derfor er den afhængigheds-frie `node:https`-variant
anbefalet.

## Regressions-risiko

- **Rør IKKE delt kode.** Patchen ændrer kun `api/_calendar.js`. De delte kaldere
  (`_booking-store.js:146` `busyFor`, `:261` `reservePart`, `clinic-portal.js:133`
  `testcal`) kalder fortsat `fetchBusy(url)` med samme signatur og returtype (`[]` eller
  liste af intervaller). Ingen API-ændring → ingen ændret kaldekontrakt.
- **Adfærdsændring at være opmærksom på:** `node:https` følger som standard ikke samme
  HTTP-detaljer som `fetch`/undici (fx automatisk dekomprimering). ICS-feeds serveres som
  `text/calendar`; hvis en udbyder svarer `Content-Encoding: gzip`, vil rå body ikke blive
  dekomprimeret af `node:https`. Hvis det observeres i drift, tilføj
  `headers: { "Accept-Encoding": "identity" }` (allerede dækket: vi sætter ikke
  `Accept-Encoding`, så de fleste servere svarer ukomprimeret), eller dekomprimér med
  `node:zlib`. Test mod de tre understøttede udbydere (Google/Outlook/Apple) før udrulning.
- **`redirect:manual`-paritet:** node:https følger som standard **ikke** redirects (vi
  håndterer 3xx eksplicit → `[]`), så SSRF-via-redirect-vektoren forbliver lukket.
- **IPv6:** `resolvePinnedIp` validerer alle adresser med `ipPrivate`, der allerede dækker
  IPv6 (linje 139-151). `node:https` forbinder fint til en IPv6-literal i `host`.
