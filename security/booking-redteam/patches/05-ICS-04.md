# Patch-FORSLAG — ICS-04 [middel]

**Status:** FORSLAG. Rør IKKE live-koden i `api/` før Lucas/Judit har godkendt.
Filerne her under `security/booking-redteam/` er rene forslag + regressionstest.

---

## Sårbarhed

**ICS-04 — Kalender-busy-tjek fail-open'er ved langsom/fejlende ICS-server → instant-booking oven i ekstern klinik-aftale.**

Den eneste beskyttelse mod at booke oven i en EKSTERN kalender-aftale på commit-stien
er `slotIsBusy(await fetchBusy(...))`-tjekket i `reservePart`. Det atomiske INCR/cap-tjek
er ægte atomisk, men kender kun Aevias egne `cnt:`-tællere i Redis og ved intet om
ICS-optaget-tider; ingen sti materialiserer eksterne busy-tider ind i `blk:`-sættet.

`fetchBusy` er bevidst **fail-open mod drift**: ved 6 s abort-timeout, non-2xx, 3xx-redirect
eller enhver exception returnerer den `[]`. `slotIsBusy([], ...)` returnerer `false`, så
busy-tjekket springes lydløst over. Oven i det swallow'er `reservePart`'s ydre
`try{...}catch(_){}` enhver fejl som et ANDET fail-open-lag.

Resultat: når klinikkens (legitime) kalender-udbyder er langsom/fejler, forsvinder det
eksterne busy-tjek lydløst, og en kunde kan instant-bekræftes (mail + .ics, ingen
pending/manuel-bekræftelses-gate) oven i klinikkens eksisterende eksterne aftale.

> Bemærk: dette er en **integritets-/driftsfejl** udløst af normale udbyder-udfald,
> ikke en ekstern-angriber-exploit. `calUrl` er klinik-styret (`saveRules → normalizeIcsUrl`),
> og udnyttelse kræver et åbnet område (`ready:true`) — alle områder i `AREAS` er pt.
> `ready:false`. Derfor **middel**, ikke høj.

## Fil:linje

- `api/_booking-store.js:257` — cache-busy-tjek (`slotIsBusy(busy, ...)`).
- `api/_booking-store.js:260-262` — live re-tjek, det relevante hul:
  `try { if (slotIsBusy(await fetchBusy(c.calUrl), ...)) return {ok:false}; } catch (_) {}`
  → `fetchBusy` returnerer `[]` ved drift-fejl → `slotIsBusy([])` = `false` → springes over;
  og `catch(_){}` swallow'er enhver exception.
- `api/_booking-store.js:264-271` — atomisk INCR/cap, der IKKE kender til ICS-busy.
- `api/_calendar.js:171-191` — `fetchBusy`: fail-open `[]` på timeout (183/190),
  non-2xx (187), 3xx-redirect (186), DNS/privat-resolve (179-180) og enhver exception (190).
- `api/_calendar.js:195` — `slotIsBusy([], ...)` returnerer `false`.

## Repro (deterministisk)

Forudsætning: et område med `ready:true` og en ydelse hvis effektive `conf` har `calUrl`
sat (klinik har tilknyttet Google/Outlook/Apple-ICS), med en EKSTERN aftale i kalenderen
der overlapper en Aevia-tid (fx tirs 09:00).

1. Kalender-serveren bliver langsom/utilgængelig (>6 s, 5xx, eller 3xx-redirect) —
   normalt udbyder-udfald, ingen angriber.
2. Kunde poster `POST /api/book-slot` med `parts=[{svc:'blod',date:<tirs>,time:'09:00'}]`
   (`book-slot.js:149 → reserveMulti → reservePart`).
3. `reservePart` cache-busy-tjek (linje 257) viser ledig (cache tom/udløbet).
4. Live re-tjek (linje 261): `fetchBusy` aborter efter 6 s / returnerer `[]`
   → `slotIsBusy([],...)` = `false` → springes over.
5. INCR (264) lykkes, `n=1 ≤ cap=1` (268) → `return {ok:true}`.
6. `reserveMulti` opretter `bk:<id>`; `book-slot.js:168-176` sender
   "Dine tider hos Aevia er bekræftet" + .ics.

Kunden er instant-bekræftet oven i klinikkens eksisterende eksterne aftale.
Determinisk reproducerbar ved at pege en testklinik-`calUrl` mod en host der
hænger / svarer 503/redirect.

## Impact

Dobbeltbooking: kunden bekræftes (mail + .ics, ingen manuel-gate) oven i klinikkens
eksisterende eksterne aftale. Resultat: spildt klinikbesøg/spildt blodprøvetid og
dårlig kundeoplevelse. Ingen dataudstilling, ingen angriber-kontrol; udløses af normale
udbyder-udfald i et snævert tidsvindue, og er pt. gated af `ready:false` på alle områder
+ nascent kalender-integration.

## Fix

**Idé:** Gør commit-stiens kalender-tjek **fail-CLOSED** (som `availability()`'s Redis-sti
allerede er, `_booking-store.js:212-217`). Behold SSRF-fail-closed uændret
(privat-resolve/redirect → afvis stille). Skel mellem:

- **SSRF-afvisning + tom kalender** → `[]` (kendt: ingen optaget-tider) → busy-tjek = ledig. Uændret.
- **Drift-fejl** (timeout, non-2xx, exception) → **sentinel `null`** (ukendt status)
  → `reservePart` behandler "ukendt kalenderstatus" som optaget → `return ok:false`.

Dette kræver to ændringer:

### 1) `api/_calendar.js` — `fetchBusy` signalerer drift-fejl som `null` (ikke `[]`)

SSRF-stierne (privat-resolve, redirect) bliver ved med at returnere `[]` (stille afvisning,
ingen optaget-tider lækkes), men de transiente DRIFT-fejl (timeout, non-2xx, exception)
returnerer nu `null` som "ukendt status"-sentinel.

```diff
--- a/api/_calendar.js
+++ b/api/_calendar.js
@@
-// Hent + parse en ICS-URL. Returnér [] ved fejl/afvisning (fail-open mod drift,
-// fail-closed mod SSRF: privat-resolvende host, redirect og timeout → []).
+// Hent + parse en ICS-URL.
+//   []   = kendt status: ingen optaget-tider (tom kalender, manglende/ugyldig URL,
+//          eller SSRF-afvisning — privat-resolvende host / redirect → stille []).
+//   null = UKENDT status (drift-fejl: timeout, non-2xx, exception). Kalderen på
+//          commit-stien skal behandle null som "optaget" (fail-CLOSED), så vi ikke
+//          instant-bekræfter oven i en ekstern aftale, vi ikke kunne tjekke (ICS-04).
 export async function fetchBusy(url) {
   const u = normalizeIcsUrl(url);
   if (!u) return [];
   try {
     const host = new URL(u).hostname;
     if (!net.isIP(host)) { // DNS-rebinding-værn: afvis hvis host resolver privat
       try { const addrs = await dns.lookup(host, { all: true }); if (!addrs.length || addrs.some((a) => ipPrivate(a.address))) return []; }
       catch { return []; }
     }
     const ctrl = new AbortController();
     const timer = setTimeout(() => ctrl.abort(), 6000);
     try {
       const r = await fetch(u, { headers: { "User-Agent": "Aevia-Booking/1.0" }, redirect: "manual", signal: ctrl.signal });
       if (r.status >= 300 && r.status < 400) return []; // følg ikke redirects (SSRF) → kendt afvisning
-      if (!r.ok) return [];
+      if (!r.ok) return null; // drift: non-2xx → ukendt status (fail-closed på commit-sti)
       return parseICS((await r.text()).slice(0, 1000000)); // cap ~1 MB
     } finally { clearTimeout(timer); }
-  } catch (e) { console.error("ICS-hentefejl:", e.message); return []; }
+  } catch (e) { console.error("ICS-hentefejl:", e.message); return null; } // timeout/exception → ukendt status
 }
```

### 2) `api/_booking-store.js` — `reservePart` behandler ukendt status som optaget

Det live re-tjek må ikke længere swallow'e fejl: hvis `fetchBusy` returnerer `null`
(ukendt status) eller selve kaldet kaster, afvises reservationen.

```diff
--- a/api/_booking-store.js
+++ b/api/_booking-store.js
@@ async function reservePart(area, svc, date, time, conf, busy) {
   if (!slotsFromConf(c, date).includes(time)) return { ok: false, reason: "Tiden findes ikke i kalenderen." };
-  // Optaget i klinikkens tilknyttede kalender? (tjek før INCR — ingen rollback)
-  if (slotIsBusy(busy, date, time, c.slot)) return { ok: false, reason: "Tiden er ikke længere ledig." };
-  // Live re-tjek mod kalenderen for den endelige commit — lukker det op-til-5-min
-  // cache-vindue, så instant-bekræftelse ikke booker oven i en ekstern aftale.
-  if (c.calUrl) {
-    try { if (slotIsBusy(await fetchBusy(c.calUrl), date, time, c.slot)) return { ok: false, reason: "Tiden er ikke længere ledig." }; } catch (_) {}
-  }
+  // Optaget i klinikkens tilknyttede kalender? (tjek før INCR — ingen rollback)
+  // null = ukendt kalenderstatus (drift) → behandl som optaget (fail-CLOSED, ICS-04).
+  if (busy === null || slotIsBusy(busy, date, time, c.slot)) return { ok: false, reason: "Tiden er ikke længere ledig — prøv igen." };
+  // Live re-tjek mod kalenderen for den endelige commit — lukker det op-til-5-min
+  // cache-vindue, så instant-bekræftelse ikke booker oven i en ekstern aftale.
+  // Fail-CLOSED: kan vi IKKE bekræfte at tiden er fri (null/exception) → afvis.
+  if (c.calUrl) {
+    let live;
+    try { live = await fetchBusy(c.calUrl); }
+    catch (_) { live = null; } // exception → ukendt status → fail-closed
+    if (live === null || slotIsBusy(live, date, time, c.slot)) return { ok: false, reason: "Tiden er ikke længere ledig — prøv igen." };
+  }
```

> Hjælpe-funktionen `busyFor` (`_booking-store.js:140-149`) cacher resultatet af `fetchBusy`.
> Med ændring (1) kan den nu modtage `null`. `JSON.stringify(null)` = `"null"`, og en
> cachet `"null"` parses tilbage til `null` — så et drift-`null` propageres korrekt videre
> til `reservePart` via `busies[p.svc]`. Det er ønsket adfærd: den prækalkulerede busy må
> ikke "redde" et drift-tilfælde. Ingen kode-ændring nødvendig i `busyFor`.

## Regressions-risiko (delt kode)

`fetchBusy` og `slotIsBusy` deles af både commit-stien (`reservePart`) OG visnings-stien
(`availability`, via `busyFor`). Tjekkede call-sites for det ændrede `[]`→`null`-kontrakt:

- **`availability()` (`_booking-store.js:201`, `218`)** kalder `slotIsBusy(busy, ...)` direkte
  på `busyFor`-resultatet. Hvis `busy === null` (drift) kaster `slotIsBusy` IKKE
  (`if (!busy || !busy.length) return false;` på `_calendar.js:195` håndterer `null`),
  men returnerer `false` → tider vises stadig som ledige. Det er en LÆSE-sti der altid
  re-tjekkes på commit, så et falsk-ledigt visnings-svar fanges fail-closed ved booking.
  **Acceptabel** — men hvis man ønsker fuld konsistens kan `availability` også udelade
  dagen ved `busy === null` (som den allerede gør ved Redis-fejl). Det er en valgfri,
  bredere ændring og er IKKE inkluderet her for at holde patchen minimal.
- **`busyFor` (`_booking-store.js:143`)** har en gren `if (!isConfigured()) return fetchBusy(...)`
  der nu kan returnere `null` — samme analyse: kun læse-sti, fanges på commit.
- **Ingen** andre interne kaldere af `fetchBusy` (grep: kun `_booking-store.js` importerer det).
- **Falske afvisninger:** ved transiente glitches vil en kunde nu se "Tiden er ikke længere
  ledig — prøv igen" i stedet for at få en (potentielt dobbeltbooket) bekræftelse. Det er
  den ønskede afvejning. Overvej en kort retry/backoff i `fetchBusy` (fx 1 ekstra forsøg)
  for at dæmpe falske afvisninger — udeladt her for at holde patchen lille og deterministisk.

## Anbefalet opfølgning (ikke i denne patch)

- Baggrunds-cron der materialiserer ICS-busy ind i `blk:`-sættet, så det atomiske
  INCR/cap-tjek bliver kalender-bevidst (lukker også det resterende TOCTOU-vindue
  mellem live-tjek og INCR).
- Evt. læg booking i `pending` (manuel klinik-bekræftelse) i stedet for hård afvisning,
  når kalenderstatus er ukendt — bedre kundeoplevelse end "prøv igen".
